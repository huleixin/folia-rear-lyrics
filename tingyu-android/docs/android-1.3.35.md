# 听屿 Android 1.3.35

本版针对用户在 1.3.34 录屏中的进出舞台抖动，保留 1.3.34 已经由用户反馈有效的歌词防闪烁方案；不更改音频输出策略、音源、歌词样式、背屏和玻璃材质参数。

## 录屏证据

逐帧检查了用户提供的 6.27 秒、约 30 fps 录屏：

- 约 0.40–0.53 秒，进入舞台前推荐页出现错位的重复内容；随后舞台头部及底栏才落到最终位置。
- 约 2.57–3.23 秒，舞台返回推荐页，页面及底栏经历分段交接；底部小播放器有一帧在偏右位置出现。
- 约 3.63 秒后再次进入舞台，重现了进入时的交接异常。

录屏只能说明实际视觉异常，不能单独证明某个 GPU 指令或图层的内部状态。以下是本轮依据代码发现并修正的交接路径。

## 修改

1. 原生小播放器点击后仍立即收起底栏，但不再直接把原生路由改到 stage、立刻把旧 WebView 画面提到上层。
2. 路由发布检查真实 AppShell 是否已经提交 `player` DOM 标记；AppShell 的布局提交负责再发布一次，避免先改 store、后提交 DOM 的间隙。
3. 原生进入舞台使用 [WebView 的视觉状态回调](https://developer.android.com/reference/android/webkit/WebView#postVisualStateCallback(long,%20android.webkit.WebView.VisualStateCallback)) 作为本次 DOM 提交的交接栅栏。在 Chromium 可绘制该提交前，保留位置稳定的原生出发页。不是切回旧版 Web UI，也不是设一个固定延时再揭开。
4. 回调带路由代次/版本校验。快速返回、重新进入、其他导航或宿主销毁后，旧回调不能重新打开舞台。进入期间系统返回也优先交给应用导航。
5. 推荐、资料库、歌单、搜索拥有画面时，WebView 的视觉层透明度为零，旧舞台不能从原生页淡入间隙透出。WebView 节点仍挂载且保持 VISIBLE，不暂停 JS、播放或后台业务；设置页的实时预览及 Web 弹层保留原显示路径。
6. 只有属于当前路由及导航代次的数据才能更新返回页留存及磁盘布局缓存；迟到的、坐标已受舞台安全区影响的首页数据不再覆盖返回位置。
7. 所有舞台与原生页之间的路由（包括歌单详情）使用同一种既有舞台转场，不再因导航深度又叠加一次水平滑动。既有收起曲线保留。

## 成本与验证边界

- 每次从其他路由进入舞台请求一次视觉状态回调；没有逐帧桥接、轮询、截图、额外常驻 GPU 层、强制预栅格化或帧率调整。
- 沿用 1.3.34 的按需硬件隔离及自动隐藏释放。该方案原有的 GPU/PCM 功耗取舍仍见上一版说明，本轮没有测量新的功耗百分比。
- 定向检查覆盖：真实 React AppShell 提交后再发布舞台、连续八轮进出音频 DOM 不重建、旧回调失效、原生路由不能露出旧 Web 像素、返回缓存不能被错位数据污染，以及现有进入/返回与音频命令回归。
- 某个旧设置测试之前没有等待它本来就依赖的下一布局帧，存在时序偶发失败；本轮补齐等待，没有修改或放宽业务断言。
- 未连接手机。本机 DOM/JVM 测试和打包不能证明 Android WebView + Compose + 小米 GPU 的抖动已消失；需要按原录屏快速进入、返回、再进入进行真机复测。
- 视觉状态回调与 Android 绘制相关，极慢设备上的交接等待时间也需要真机确认。本版选择保持出发页稳定，不以强行显示旧 Web 帧作为超时兜底。
